# Moonflow — Technical Design Doc

The concrete blueprint that bridges the ADR log's decisions and the design system's rules into actual code structure.

## Dexie Schema

```js
// db.js
import Dexie from 'dexie';

export const db = new Dexie('MoonflowDB');

db.version(1).stores({
  entries: 'date',    // primary key = "YYYY-MM-DD" date string — one row per day, upsert by date
  settings: 'key'      // simple key-value table for app config
});
```

**`entries` row shape:**
```js
{
  date: '2026-09-04',        // primary key, date-only (see ADR-012)
  flow: 'light',              // null | 'spotting' | 'light' | 'medium' | 'heavy'
  symptoms: ['cramps'],       // array of symptom ids
  mood: 'smile',               // null | 'cry' | 'sad' | 'neutral' | 'smile' | 'happy'
  note: '',                    // free text
  updatedAt: 1757000000000    // ms timestamp, bookkeeping only — never used for date math
}
```

**`settings` rows** (key-value pairs):
| key | type | default |
|---|---|---|
| `onboardingComplete` | boolean | `false` |
| `lastPeriodStart` | date string | — |
| `avgCycleLength` | number | `28` |
| `avgPeriodLength` | number | `5` |
| `pinHash` | string \| null | `null` |
| `pinLockEnabled` | boolean | `false` |
| `soundEnabled` | boolean | `false` |
| `draftEntry` | object \| null | `null` — cleared once a real save succeeds |

Future fields (BBT, ovulation-test results, etc.) get added in a `db.version(2).stores({...})` block per Dexie's migration model — never by mutating version 1 in place.

## Rendering Note (see ADR-017)

`index.html` is not fully empty — the tab bar is written as real, static HTML directly in the page, since it's identical on every screen and never depends on user data. Only the main content area is generated by `app.js` after reading from IndexedDB. This is the one piece of the app that paints before any JS executes.

## Theming Rule (what makes a future theme plug-and-play)

Every color in `components.css`/`screens.css` must reference a token — zero hardcoded hex values outside `tokens.css`. A theme is just a second variable block:

```css
/* tokens.css */
:root, [data-theme="dark"] {
  --bg-screen: #14132B;
  --text-primary: #F5F3EC;
  --glass-fill: rgba(72,68,120,0.45);
  /* ...rest of the frozen palette */
}

/* Future light theme stub — values need real design work, not a mechanical inversion,
   especially --glass-fill, which is tuned for the dark background specifically. */
[data-theme="light"] {
  --bg-screen: /* TBD */;
  --text-primary: /* TBD */;
  --glass-fill: /* TBD — needs its own tuning, not an inverted value */;
}
```
Switching themes at runtime is one line: `document.documentElement.dataset.theme = 'light'`.


## Cycle-Math Algorithms (pseudocode)

```
function derivePeriods(entries):
  periodDays = entries.filter(e => e.flow in ['light','medium','heavy'])  # spotting excluded — ADR/edge-case rule
              .sortBy(date)
  periods = []
  current = null
  for day in periodDays:
    if current == null:
      current = { start: day.date, end: day.date }
    else if daysBetween(current.end, day.date) <= 2:   # gap tolerance
      current.end = day.date
    else:
      periods.push(current)
      current = { start: day.date, end: day.date }
  if current: periods.push(current)
  return periods

function predictNextPeriod(periods, settings):
  if periods.length < 2:
    return { date: lastKnownStart + settings.avgCycleLength days, confidence: 'estimated' }
  lengths = [daysBetween(periods[i-1].start, periods[i].start) for i in 1..periods.length-1]
  med = median(lengths)
  variability = stdDev(lengths)
  predicted = periods.last().start + med days
  if variability > 4:  # days — threshold for "too irregular to promise a date"
    return { rangeStart: predicted - variability, rangeEnd: predicted + variability, confidence: 'wide' }
  return { date: predicted, confidence: 'confirmed' }

function estimateFertileWindow(nextPeriodDate):
  ovulation = nextPeriodDate - 14 days   # luteal phase is far more consistent than follicular — standard heuristic
  return { start: ovulation - 5 days, end: ovulation + 1 day, peak: ovulation }
```

Averages throughout use the **median**, not the mean (ADR-driven — one outlier entry shouldn't skew every future prediction).
